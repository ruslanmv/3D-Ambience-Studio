# Route 2 — generating backplates directly

A second output shape beside the 360° panorama, for runtimes that draw a **flat**
background rather than a skybox.

Additive: the panorama path is untouched, and a project can be published as
either or both.

## Why

3D-Avatar-Chatbot assigns a flat image to `scene.background` and crops it to the
viewport. Feeding that a panorama is a poor deal twice over.

**It is lossy.** A 30° vertical field of view at 16:9 is **50.9° horizontal**, so
a 4096-wide panorama contributes about `4096 × 50.9/360 ≈ 580 px` to an image
stretched to 1920 — a seventh of the source, upscaled 3.3×. Landing 1920 real
pixels would need a panorama roughly 13,600 px wide.

**It is uncontrolled.** A panorama generated as a 360° sky has no reason to keep
the middle of any particular view clear, so the character ends up with a tree
through her head.

Generating the backplate directly fixes both: every pixel is in the final image,
and the generator can be told where the horizon and floor must be.

## How the numbers get here

```
runtime camera ──► contract JSON ──► guide image ──► provider ──► backplate
CalibrationGeometry   examples/         horizon,        worker      1920×1080
     .js              backplate-        floor,
                      camera/           keep-clear
```

The Studio **computes no projection**. Every figure is read from a camera
contract the consuming runtime exported from its own live camera
(`schemas/backplate-camera.schema.json`). A second implementation of the
projection is exactly how the two would quietly stop agreeing.

For 3D-Avatar-Chatbot that contract is generated by
`tools/ambience/export-camera-contract.mjs` and committed at
`assets/ambient/camera-contract.json`; a copy lives here at
`examples/backplate-camera/avatar-chatbot.json`.

### The horizon is not at mid-frame

The single most important number in the contract. That runtime's camera is
lifted by `normalize(0, 0.03, 1)` — a **1.72° downward tilt** — which puts the
horizon at **44.4%** of frame height, not 50%. A generator conditioned on a
mid-frame horizon is 60 px out on a 1080 master, and the floor will not meet the
character's feet.

`pitchDeg` is in the contract precisely so nobody has to know that to get it
right.

## The guide image

Text is weak for geometry: "thirty degree vertical field of view" is not
something a diffusion model can act on. A *picture* of the constraint is, which
is the finding behind ControlNet and T2I-Adapter — spatial conditions control
structure, prose does not.

`services/backplate_guide.py` draws, on black:

- the **horizon**, in red
- **depth lines** at the contract's ground distances
- **longitudinal lines** converging on the vanishing point — the cue that makes a
  floor read as a floor. Drawn without any projection maths: a straight line in
  the world projects to a straight line in the image and all of them pass through
  the vanishing point, so each is a segment from the bottom edge to
  `(footAnchor.x, horizonY)`.
- the **keep-clear box**, where nothing prominent may go
- the **foot-contact point**

`build_prompt()` puts the same facts in words for workers that accept no image
condition, plus a negative prompt carrying the two rules with no positive
phrasing: no characters, and no cast figure shadows. A painted person duplicates
the avatar; a painted shadow will not match where she is standing.

## Providers

| id | role |
| --- | --- |
| `mock-backplate` | Built-in. Draws sky and ground **to the guide's own horizon**, so it verifies the chain with no GPU and no network. Not AI generated, and the provenance says so. |
| `backplate` | HTTP adapter to an external worker. |

Worker contract:

```
POST {base_url}/generate
  {prompt, negative_prompt, width, height, seed, guide_png_base64?}
response = image bytes, or JSON with download_url
```

The guide goes inline as base64 rather than as a URL: a worker is typically on a
private network with no route back, and a conditioning image that fails to fetch
would degrade silently into an unconditioned generation that looks fine and does
not line up.

A worker may ignore `guide_png_base64` — the prompt carries the same constraints
in words. It will produce worse results.

## Pipeline differences from the panorama path

| | Panorama | Backplate |
| --- | --- | --- |
| Shape check | 2:1 within 1% | the profile's aspect within 2% |
| Upscaling | **never** | **yes**, to the master |
| Off-size input | rejected | centre-**cropped**, never resized |

The wider tolerance is because generators quantise to multiples of 8 or 64, so
1920×1088 is a rounding artefact rather than a wrong shape. It is cropped rather
than resized because resizing would move the horizon off the row the contract put
it on — the one thing that must not move.

Upscaling is allowed here and forbidden there because a backplate **is** the final
image: shipping it small only moves the upscale into the browser, where it happens
on every load and looks no better.

## Using it

```python
await workflow.generate_backplate(project_id, "mock-backplate", contract_path, "landscape")
workflow.optimize_backplate_asset(project_id)
```

The guide is written into the project directory and kept. When a backplate turns
out not to line up, it is the only evidence that distinguishes *the guide was
wrong* from *the worker ignored it*.

## What this does not solve

**Art direction.** The guide constrains geometry, not taste. A model can satisfy
every line and still produce something ugly, or something whose lighting fights
the character's.

**Lighting agreement.** The consuming runtime lights its character independently —
3D-Avatar-Chatbot's background manager deliberately never touches lights or
`scene.environment`. Until per-scene lighting metadata is consumed, author scenes
that sit comfortably with a default key/fill/rim setup.

**A worker.** `workers/` is still a README. `mock-backplate` is the only provider
that runs today, and it draws gradients, not art. The HTTP adapter is ready for a
worker that does not yet exist here.
