# 03 — Licensing review

Covers task section **E** and the mandatory inventory of **§14**. Engineering review,
not legal advice; anything marked as a gate needs a human decision recorded against it
before production use.

Verified **2026-09-11** against primary sources (repository `LICENSE` files, Hugging Face
model cards, dataset EULAs). Facts that could not be reached from a primary source are
marked `UNVERIFIED` and **must not** be relied on.

---

## 3.1 The rule that the whole review exists to enforce

```
repository licence  ≠  dependency licences
                    ≠  model-weight licence
                    ≠  training-dataset terms
                    ≠  rights in the generated output
```

Four of the five projects the brief proposed for the generation path fail precisely at
the join between two of these layers. The failure mode is always the same shape: **a
permissive repository licence over restrictively-licensed weights.** A fork cannot fix
it, an adapter cannot fix it, and Dockerising it cannot fix it.

---

## 3.2 Finding 1 — DreamScene360 is non-commercial

`ShijieZhou-UCLA/DreamScene360` ships `LICENSE.md` containing the **Inria / MPII
Gaussian-Splatting research licence**. Verified clauses:

- Licensor is *"the owners of the Software, i.e. Inria and MPII"*.
- Grant is *"non-exclusive rights to use the Software for research purposes to research
  users (both academic and industrial), free of charge"* — *"for research and/or
  evaluation purposes only"*.
- **"THE USER CANNOT USE, EXPLOIT OR DISTRIBUTE THE SOFTWARE FOR COMMERCIAL PURPOSES
  WITHOUT PRIOR AND EXPLICIT CONSENT OF LICENSORS."**
- No right to sublicense. Redistribution only under the same licence, with a complete
  copy included.

**Consequences.**
1. DreamScene360 cannot be a production provider, forked or not.
2. Publishing environments generated by it to a CDN for an end-user-facing product is
   outside the grant — even internally generated output should be treated as
   evaluation-only and never published.
3. **It contaminates Text2VR.** Text2VR is MIT at the top level and integrates
   DreamScene360 as its panorama stage. Using Text2VR's pipeline end-to-end means using
   DreamScene360. The brief's instruction to audit Text2VR's dependency tree before
   trusting its MIT badge was correct, and this is the hit.
4. The entire 3D Gaussian Splatting lineage inherits this licence. That independently
   justifies deferring Gaussian Splatting (brief §63) on legal grounds, before any
   technical argument about Quest performance.

## 3.3 Finding 2 — PanFusion's MIT code sits on non-commercial weights

- Repository code: **MIT** (verified).
- Training data: the **Matterport3D** skybox dataset, which requires a signed Terms-of-Use
  submitted from an institutional email address before the download script is released.
- Matterport3D is licensed for **non-commercial academic use**; models trained on it are
  distributed under Matterport3D's Terms of Use and **CC BY-NC-SA 3.0 US**.

So the released checkpoint is a derivative of non-commercially-licensed data, and
CC BY-NC-SA additionally imposes *share-alike*. The code licence is irrelevant to the
question we actually care about, which is whether we may publish the pixels.

**This corrects a recommendation already present in this repository.** `README.md` and
`docs/OPEN_SOURCE_INVENTORY.md` both name PanFusion as the first V1 panorama adapter
candidate, with the caveat "model weights must be audited". The audit has now been done
and the answer is no. Those files are corrected in §3.6.

The same reasoning applies, pending verification, to **MVDiffusion** and to **DiT360**
(MIT code, *refined Matterport3D* training data, ~37 GB VRAM, 1024×2048 output).

## 3.5 Tooling licences that affect what we may *distribute*

These matter because we will ship Docker images and a published product, not just run
scripts.

| Tool | Terms | What it means for us |
|---|---|---|
| **Blender** | GPL | Invoking `blender --background --python script.py` as a separate process is fine and does not make our code derivative. Bundling Blender into a redistributed image, or linking it, triggers GPL obligations. Our Blender scripts use Blender's Python API — keep them generic, free of proprietary business logic. |
| **FFmpeg** | LGPL-2.1+ by default; **GPL if built with `--enable-gpl`** (as most distro/`ffmpeg.org` static builds are) | If we redistribute a worker image containing a GPL FFmpeg build, the image carries GPL terms. Mitigation: pin an LGPL build, *or* keep FFmpeg confined to a private build worker we never redistribute. Decide once and record it. |
| **libvips** | LGPL-2.1 | Fine as a dynamically-linked library via `pyvips`. Do not statically link into a closed binary. |
| **libopus** | BSD-3-Clause | No constraint. |
| **Basis Universal / KTX-Software** | Apache-2.0 expected, `UNVERIFIED` — KTX-Software bundles Basis and ships a `LICENSES/` directory plus `NOTICE.md` that must actually be read | Gate before V1 ships, since KTX2 is a V1 production dependency. Apache-2.0 would also impose NOTICE-propagation duties. |
| **meshoptimizer**, **Draco** | MIT / Apache-2.0 expected, `UNVERIFIED` | Gate before V2. |
| **Three.js r0.147.0** (vendored in the avatar repo) | MIT | No constraint; note the vendored copy means avatar-side upgrades are a deliberate act. |

## 3.7 The mandatory provider gate (§14, hardened)

No provider may be enabled in a production pipeline until its inventory row records
**all** of the following, with a named owner and a date:

```
Component            Version / commit
Source               repository or vendor URL
Code licence         SPDX, read from the LICENSE file — not the GitHub badge
Weights licence      read from the model card / checkpoint distribution
Training data        dataset name + its own terms, and whether they follow the weights
Commercial use       yes / no / conditional — with the clause quoted
Redistribution       may we serve derived output from a CDN?
Share-alike          does any NC/SA term attach to our output?
Attribution          exact text required, and where it is surfaced
Output rights        who owns generated pixels; any vendor licence-back
Patent / codec       any encumbrance on the formats produced
Decision             ENABLED / EVALUATION-ONLY / REJECTED, owner, date
```

Three rules make this gate real rather than ceremonial:

1. **A GitHub licence badge is not evidence.** It reflects the root `LICENSE` file only.
   DreamScene360's own root file is the counterexample: the badge tells you nothing
   about Inria's terms.
2. **Weights and data are audited separately from code, always.** PanFusion is why.
3. **`UNVERIFIED` blocks production.** A row may sit at `UNVERIFIED` indefinitely for an
   evaluation-only component; it may never be promoted to `ENABLED` while it does.

## 3.8 Per-asset rights metadata

Every asset the Studio ingests or produces carries provenance in **private** metadata
(never in the public manifest — see `05-CONTRACT-SCHEMAS.md` §5.5):

```
source            uploaded | provider:<name> | purchased | commissioned
author / vendor   who made it
licence           SPDX or contract reference
commercialUse     boolean, with the basis recorded
attribution       required text, and whether the runtime must display it
modified          did we alter it, and how
generator         provider, model, model version
generatedAt       timestamp
prompt / seed     for reproducibility
audioSource       separate row — ambience is the most common rights failure
```

The public manifest may carry a short `credits` block **only** where attribution is
contractually required. Everything else stays internal: publishing the model version
and seed invites the runtime to care about the generator, which is the coupling this
whole architecture exists to prevent.

## 3.9 Generated-output rights: the question people forget

Even with permissive code and weights, three questions remain open per provider and must
be answered in the row:

1. **Who owns the output?** For self-hosted open weights, generally the operator — but
   OpenRAIL-family licences (the Stable Diffusion lineage under every panorama candidate
   here) attach **use restrictions** that travel with the model and its derivatives.
   Those restrictions are about prohibited uses, not ownership; our calm-ambience use
   case sits comfortably inside them, and that judgement should be recorded rather than
   assumed.
2. **Does the vendor take a licence back?** Commercial APIs commonly do — the Skybox AI
   terms grant the vendor a perpetual non-exclusive licence to content created with the
   service. Acceptable here; record it so nobody rediscovers it during a due-diligence
   exercise later.
3. **Is a free tier export-licensed at all?** Often not. A free-tier export has no usable
   licence, commercial or otherwise, and must never enter the catalogue.

## 3.10 Net licensing position

- **V1 as planned is clean**, because every V1 component is a deterministic tool
  (libvips, FFmpeg/Opus, KTX-Software, glTF Transform) plus creator-supplied or
  commercially-licensed art. Two gates remain open: the FFmpeg build choice and the
  KTX-Software/Basis `NOTICE` read.
- **The open-weights panorama path is currently blocked.** Nothing among DreamScene360,
  PanFusion, MVDiffusion or DiT360 has a verified commercial route. Diffusion360
  (Apache-2.0 code) is the only live candidate and is gated on its weights audit.
- **V2's image-to-3D path is clean** (TripoSR and TRELLIS, MIT code and MIT weights),
  with one open item on TRELLIS's submodules.
- **Gaussian Splatting is rejected on licence grounds**, independent of performance.

The architectural conclusion: the provider boundary is not an elegance exercise. It is
the mechanism that lets the product ship while the legal status of generation models
stays unresolved.
